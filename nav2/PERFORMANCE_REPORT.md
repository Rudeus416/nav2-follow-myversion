# R38：途中视觉超时的资源与计算开销修复

对应用户指令：“监测日志，这次小车停止的原因是什么”之后的“能不能修复这个问题”。本次仅修改自有 `nav2/`，没有修改原控制、相机、启动脚本、原前端、根目录 `nav2_follow.py` 或外部库；没有重启服务或发送行驶命令。

## 日志能确认什么

2026-09-29 13:12:17.562 接受 FollowPath，13:12:28.663 由客户端取消，任务持续约 11.101 秒（包括暂停时间）。`data/runtime/control.log:257` 明确记录 **“视觉障碍数据持续超时，取消导航”**。`nav2.log:207–210` 没有报告本次终点不可达或控制器碰撞失败。

同轮 `control.log:296` 的帧 340 首次读取年龄为 **2.769 秒**，推理阶段 **2.671 秒**，邮箱等待仅 **0.001 秒**，相邻结果间隔 **3.049 秒**。原 `inference` 计时包括模型预测和深度张量转 CPU/NumPy，并非纯 GPU 内核耗时。其他帧也曾出现导航几何阶段开销，因此同时优化自有处理。

这些数据证明视觉源更新太迟而触发保护，不能单凭日志认定整个延迟都由某个模型造成。此次又确实复现了一个自有资源限制失效问题：设置 PyTorch 单线程后，附加 YOLOE 首次 CPU 后端初始化调用本机 Ultralytics `select_device('cpu')`，把线程数重新设为 **7**。原限制失效会增加与深度处理竞争资源的风险。没有改动这段第三方源码。

## 自有修复位置

| 文件 | 修改与理由 |
|---|---|
| [semantic_runtime.py](semantic_runtime.py) | 仅在自己的 multiprocessing 子进程内限额。后端初始化完成后重新限制 PyTorch、OpenCV、BLAS/OpenMP 为单线程，子进程现有线程和新线程使用 nice 至少 10。模型使用自有子类；不修改第三方全局类或原人物/深度模型。 |
| [semantic_budget.py](semantic_budget.py) | 根据深度源年龄与实际结果间隔，暂停附加 YOLOE 的新任务，给主深度链路留出资源；加载的模型和在途响应保留。 |
| [semantic_request.py](semantic_request.py)、[semantic_obstacles.py](semantic_obstacles.py) | 原采集时间随请求入队；排队后、模型初始化后、预处理后实际 forward 前分别检查原 1.2 秒新鲜度。过期任务显式确认丢弃，释放 pending，下一新帧可继续。资源暂停仍收取结果，状态同时保留模型故障原因。 |
| [depth_groups.py](depth_groups.py)、[vision_layer.py](vision_layer.py) | 最近障碍碎片由逐标签扫描/百分位计算改为一次分组排序。保留原第 10 百分位、距离与合并门槛、种子及像素选择；不降低栅格分辨率，不削减障碍保护范围。 |

### 预算暂停如何恢复

下面只决定是否启动额外语义识别，不决定小车是否可以运动：

- 源帧年龄超过 0.85 秒，或者“结果完成时的源年龄 + 上次结果完成间隔”超过 1.05 秒，暂停新语义任务。数据缺失、未来时间、非有限值、同一流乱序也暂停。
- 暂停后，需要连续 5 个不同的健康观测，且距最后一次压力事件至少 3 秒才恢复；健康要求年龄不超过 0.65 秒、上述预计年龄不超过 0.85 秒。重复轮询同一帧不能补足确认次数。
- 不反复卸载/重载模型，也不强杀已经开始的单次推理；它仍可能消耗时间。排队或预处理期间已经过期的输入会跳过实际预测。
- 新日志为 `附加语义预算：暂停新任务，深度避障继续` / `允许新任务`，包含源年龄、结果间隔、预计年龄和恢复计数。暂停时语义分类辅助可能暂缺，深度近距检查与障碍地图处理继续。

**原运动保护保留：源数据超过 1.2 秒先零速，最后有效源数据超过 2 秒仍取消。** 历史人物点、固定路段终点、1 米连续追踪规则和原运动参数没有调整。

## 验证

- 完整离线回归 **460 项通过，18.942 秒**，在 R37 的 418 项上增加 42 项。覆盖线程限制在后端重建后仍生效、过期请求响应、暂停/恢复、去重、子进程诊断与精确几何对照。
- 原有 **14 条时序模拟**和线程竞争探针通过。350 毫秒发布阻塞下，速度出口约 0.133 毫秒返回；这是离线注入，不是实车实时性保证。
- 80×60 / 300 标签合成样例中，碎片选择的中位耗时 **63.879 → 3.680 毫秒**；逐像素等价检查通过。这只是该步骤，不代表整个检测链路加速同样倍数。
- 独立资源探针用真实模型 `forward_pre_hook` 采样：实际首次 forward 前，PyTorch/interop/OpenCV 与全部 4 个已加载 BLAS/OpenMP 池均为 1，线程 nice 均为 10。仍有 7 个 OS 线程存在，不代表计算池并行度为 7。该资源探针首次 predict 3.259 秒；随后补入过期检查，另用下述完整 worker 探针验证丢弃与恢复。
- 真实本地 YOLOE、CPU、合成图片的隔离工作进程：排队过期帧返回 `dropped`；首次新帧在懒初始化/预处理后过期也返回 `dropped`；后续新帧成功返回 `result`（该次调用 1.177 秒）。证明丢弃不会卡死后续任务，不是实车检测精度测试。
- 原控制、相机、启动脚本、原前端和根目录导航入口的 SHA-256 与本轮开始一致。

原始汇总数据见 [R38 验证结果](tests/performance_results_r38_20260929.json)，保留之前 R36/R37 的结果文件。

# R40：优化人物追踪中的视觉更新与路径复核

对应用户要求“优化”“继续”，沿用仅修改自有 `nav2/` 的范围。

## 原因与证据边界

用户确认：选点正常时没有勾选视觉障碍检测。当前日志两次人物追踪均由控制器接受 FollowPath，分别约 15.701 秒、2.551 秒后被接入层以“视觉障碍数据持续超时，取消导航”终止；不是人物历史位置消失或没有规划出路线。

实际深度结果已使用 512。帧 883 首次读取时年龄 0.340 秒、推理 0.105 秒、邮箱等待 0.002 秒，而该次视觉 tick 0.799 秒。代码确认同帧投影/连通域重复执行，人物模式还在视觉线程同步复核剩余路线。它们是可消除的额外开销；旧计时把构图、发布、锁等待和路线复核合计在一起，不能把整个 0.799 秒都归因于其中某个函数。上游也出现慢推理，本轮不保证消除所有延迟尖峰。

## 修改方式

1. `depth_projection.py`：单帧共享去畸变、坐标投影、基础支撑筛选。最近物体深度分组在首次需要时计算，地图为空时的相机回退复用它。每次筛选复制掩膜；全量近距点不受地图边界或最近物体筛选裁剪。
2. `route_monitor.py`：剩余全路径复核交给一个惰性启动的工作线程，最多一条待处理通知。视觉线程继续处理新帧；近距保护和速度出口的完整扫掠仍同步执行。复核结果不直接授权运动。关闭、配置代次、任务/路线/段改变或源快照更新后，旧结果不能触发停止或绕行新任务。
3. `replan_safety.py` / `replan_support.py`：控制锁外每帧整理 5 cm 障碍单元及完整车身，保存不可变副本。路径和速度复用输入，不复用判定结果；每次使用当前位姿、真实输出速度与源时间重新检查。先校验整条路径及采样预算，再以保守外包范围排除不可能接触的单元；可能接触时仍走原完整转角扫掠。
4. `vision_layer.py`：新增 `phases` 和后台 `route_monitor` 耗时，车身读取用 `footprint_seconds` 表示，避免把地图/TF 准备全部误标成“导航锁等待”。沿用原只读接口和限频日志，没有添加前端轮询。

没有改变历史人物终点、连续追踪条件、地图/紫色区域、车身尺寸、运动速度、制动模型以及 1.2 秒零速/2 秒取消策略。新代码须停车后通过 README 的原启动命令重启加载；本轮没有执行实车运动或代为重启服务。
