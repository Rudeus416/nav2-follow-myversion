## 1. 记录边界

本文件按用户要求整理“我们的对话、回复、修改理由和代码来源”。它是一份**可公开、可审计的工程记录**，不是平台的逐字聊天导出，也不是 Git 提交历史。

记录遵守以下边界：

1. 用户指令取自当前会话中仍可见的消息，引用处尽量保留原话；重复的“修改”“继续”“修复”等短指令会与当时上下文合并记录。
2. 助手回复无法从仓库完整恢复时，只记录当前源码、日志、README、测试和现有 `CODE_GUIDE.md` 可以支持的结论，不补写未保存的逐字回复。
3. 不记录模型隐藏的逐 token 思维过程、内部草稿、系统提示、开发者提示或安全审查细节。下文的“公开分析”只包含能够向用户说明并由文件、日志、配置或测试复核的依据。
4. “R01～R42”是本项目为了关联需求、代码和测试而建立的人工索引，不是 ROS/Nav2 版本号，也不是平台消息 ID。
5. 早期某个函数究竟在哪一轮首次出现，若没有提交历史或历史 diff，不能仅凭当前文件证明；本文件描述其**当前职责**以及与需求的关系。
6. 离线测试通过只说明给定模拟输入下的行为；它不等于实车、真实相机、雷达、CAN、TF 和地面环境已经验证。
7. 用户多次限定“只修改你自己写的 nav2 代码，不要修改别人旧代码库”。本文把它作为持续生效的范围约束；生成物、第三方模型、系统 Nav2、Ranger 驱动和旧业务代码不归为自有源码。

证据优先级如下：

1. 当前日志中的时间、动作状态、错误码和错误文字；
2. 当前源码、参数和测试；
3. 当前 README、AUDIT、PERFORMANCE_REPORT、SIMULATION_REPORT 与 CODE_GUIDE；
4. 会话中用户对现场现象的描述和截图；
5. 无法从以上内容复核的推测必须标为“待实车确认”。

## 2. 对话时间线：从能动到建立独立 Nav2 导航

### 2.1 底盘切换、目标超时和最初的不动问题

用户先确认“切换成功，动起来了”，随后询问下一步，以及为什么已经有停车路径预览，开启跟踪后仍显示“目标跟踪数据超时”。随后又连续提出：

- “nav2日志里的路径规划报错是什么”
- “先修改无障碍物时不能跟踪我的问题吧”
- “开启自动跟随后小车轮子一直摇摆但是不往前走，规划的路径一直在闪”
- “路径没怎么更新，小车为什么还是不动，小地图上看到路径也很快消失了”
- “小车不动了，监测报错”
- “是不是雷达监测有问题……一直修改路径”

公开处理结论逐步从“路径是否存在”转向完整控制链：规划成功只表示有几何路线，车辆是否运动还取决于动作是否被接受、TF/里程计是否新鲜、视觉或雷达是否超时、近距保护是否停车、强停是否解除，以及速度是否真正进入底盘发布通道。路径闪烁可能来自目标或障碍数据变化，但不能只凭闪烁断言是雷达故障。

这阶段建立的长期原则是：

- 规划、路线复核和执行分开；
- 无新目标数据时不能把旧测量冒充新测量；
- 运行中的安全超时必须输出零速度；
- 诊断必须保存具体拒绝原因，而不是只显示“未激活”或 HTTP 409；
- 只根据一次截图不能证明传感器硬件损坏。

### 2.2 从雷达探索转向静态手绘地图

由于现场暂时无法测清空地雷达，用户询问：

- “nav2是不是有直接画地图替代雷达自己探索的方式”
- “我暂时测算不了空地雷达，直接进行方案2，开始测试静止地图吧，slam怎么画”
- “手绘地图应该用什么软件”

公开回复区分了两类方法：

- SLAM：依靠传感器和里程计建立地图；
- 静态手绘地图：按实测比例生成 PGM/YAML，直接给 Nav2 的 map server 使用。

用户随后提供走廊瓷砖示意图，并指定：

- 走廊约宽 2.1 米、长 4.2 米；
- 小车朝上；
- 小车放在最下面三块整砖的中间一块；
- 地图左右翻转，但小车位置不动；
- 把地图加入自有程序。

公开工程理由是：Nav2 可使用静态占用图，不要求先在线 SLAM；但地图比例、原点、方向和初始位姿必须一致。格线示意图不能直接当障碍图，因为内部格线会被识别为墙，所以导航图只保留真实墙体/禁区。

### 2.3 模式选择和启动说明

用户要求雷达模式、地图模式可以单独或同时开启，并把启动信息放到 `nav2/README.md`。由此形成 `radar`、`map`、`both` 三种障碍来源，以及视觉障碍独立开关。当前 README 把所有启动命令放在统一小节，并明确视觉障碍不带参数时默认关闭。

公开原因是：静态地图提供固定边界，雷达提供动态测量，两者可以独立验证；模式必须在启动时固定，避免行驶中切换造成代价地图来源不一致。

### 2.4 网页地图、手绘禁区和曾撤回的照片上传

用户要求网页显示：

- 地图；
- 小车当前位置与朝向；
- 预计路线；
- 人为添加的黑色阻挡区；
- 鼠标或手指连续绘画，而不只矩形；
- 缩小紫色显示范围。

随后用户提出“现场上传大地图并选择小车大概位置”，在澄清为“普通照片或截图，只用于标注预览”后，又明确要求：

> 算了，撤回你刚刚做的关于上传照片的所有改动

因此，照片上传属于**已撤回需求**，不应作为当前导航地图输入。公开原因是普通照片没有可靠的米/像素比例、原点和占用语义，最多适合预览，不能直接授权导航。

网页手绘保留的设计是：输入经过尺寸、边界和地图版本校验，合成到自有编辑地图；清除手绘禁区只清除用户图层，不应清除独立视觉候选。

### 2.5 红色手绘虚拟墙、黄色视觉墙与最近障碍

用户要求手绘禁区在相机画面中显示浅红色虚拟墙，并反复限定：

- 仍在自有 Nav2 内实现；
- 不影响原相机功能；
- 在地图旁新增预览；
- 黄色视觉墙与红色手绘墙合并在同一个预览窗口；
- 虚拟墙只在墙体或车位变化时更新，静止时不持续重算。

接着，用户要求相机检测障碍、估计位置并加入小地图，并提出“只有突然出现且无法躲避时停车，可以绕行就绕行”。现场截图暴露了多类问题：

- 没画禁区却出现大块红区；
- 地图两侧墙丢失；
- 地图外候选被画回地图；
- 最近椅子或手推车没有被选中；
- 黄色相机墙和小地图红区不匹配；
- 清除手绘禁区后黄色墙也消失；
- 黄色墙位置与真实最近物体不一致。

公开分析把三种数据分开：

1. 静态地图/手绘禁区：导航坐标中的固定障碍；
2. 深度或语义视觉候选：相机帧中的动态障碍；
3. 虚拟墙预览：投影显示，不等于原相机画面，也不能单独作为底盘授权。

“黄色看起来更符合实际”不代表可跳过坐标标定。图像里的近不等于地图里的近，必须结合深度、相机内参、安装位姿、TF 和地图边界。Nav2 本身不做物品分类；YOLO/YOLOE 负责语义分类，Nav2 负责代价地图、规划和控制。

### 2.6 选点执行、整车净空和紫色缓冲

用户在能预览路径后要求增加“开始行驶”。随后出现：

- Nav2 未激活；
- 按开始后不动；
- 走一小段就停；
- 倒退目标时转圈、只偏一点后停；
- 路径更新太快，原地微调；
- 障碍不紧急时不要换路径；
- 紫色缓冲可完全关闭并可滑动调整；
- 缓冲为 0 仍显示紫色；
- 规划路线贴着障碍，小车前端会碰。

公开处理把两种净空分开：

- **车身基础轮廓**：即使额外紫色半径为 0，完整车身仍必须避障；
- **额外紫色硬缓冲**：在车身之外再增加用户可调的禁入距离。

因此，“紫色半径 0”不能理解为点机器人，也不能关闭完整车身碰撞检查。路径最短不是唯一目标；每个候选姿态、转弯扫掠和实际速度轨迹都要能容纳整车。额外紫色缓冲启用时，整车也不得进入该区。

用户再次强调不要修改别人旧库，若先前碰到旧库则撤回，改在自有代码实现。当前方案使用 `nav2/whole_body/` 自有插件及 Python 复核层，不修改系统安装的 Nav2 源码。

### 2.7 人物图标、历史点、单段追踪和连续追踪

用户要求：

- 检测到人物后，把人物位置作为路线终点；
- 已选人物显示橙色三角形；
- 人物闪烁或短暂遮挡时保存最近位置；
- 点击“记录人物点并规划”后立即冻结历史点并往那里规划；
- 预览成功后增加“开始追踪”；
- 人物没有明显移动时终点不变；
- 抵达该目标点后才寻找下一位置；
- 连续模式在 1 米内等待，人离开 1 米后继续；
- 途中只有突然障碍触发停车/绕行，不能因人物每帧变化反复改线；
- 取消追踪后结束循环。

用户明确确认的期望链路是：

1. 选择人物；
2. 保存同一人物最近有效位置；
3. 点击开始追踪后执行已锁定路线；
4. 途中出现新障碍先停车；
5. 能绕行则保持原历史终点重规划，不能绕行则继续停车；
6. 抵达历史终点后，若连续追踪未取消，再读取新的有效人物位置；
7. 距离小车不大于约 1 米则等待；超过 1 米再规划下一段；
8. 取消模式后停止续段。

公开分析指出，实时图标可以因短时检测抖动隐藏，但锁定历史点和已复核路线不能因此被删除。历史点不应受 3 秒图标显示时限限制；连续下一段仍必须用到达后得到的新观测，不能无限复用旧点。

### 2.8 多轮“不动/途中停止”的证据链

用户多次报告“有路径但不动”“弯道停”“第二个转弯口前停”“修完又不前进”。公开排查没有把所有现象归为一个原因，而是从日志中区分：

- 用户主动取消的成功动作；
- 规划成功但执行动作未接受；
- TF/里程计超时；
- 视觉数据超过运行时门槛；
- 深度推理速度跟不上；
- 近距危险立即停车；
- 路径复核线程或锁竞争拖慢新帧；
- 底盘测试后断电/拔线导致 CAN 状态无法代表运行时故障。

用户确认一次 `can0 ERROR-PASSIVE` 是测试后已关闭底盘或拔线，因此那次状态不能用来证明车辆行驶时的根因。后续通过独立 TF 接收、最新深度邮箱、短锁提交、异步路线复核和深度输入 512 等方式逐项降低软件内部延迟，但仍保留“现场复测”的边界。

### 2.9 前端整理、地图平移和撤回范围

用户要求视频集中、按钮有序，随后马上要求：

> 撤回修改，不要修改别人的前端，你只用优化你自己写的代码的  
> 只整齐排版你的nav2面板

因此，曾经考虑的全页工作台、固定强停栏和独立页面入口均属于**已撤回实现方向**。当前只整理自有 `.obstacle-map-panel`，保留原页面其他区域。

随后增加地图上下、左右移动，且用户确认电脑端强制刷新后已经看到。平移只改变显示视口；地图、车身、人物、障碍、路线和选点逆变换必须共用同一偏移，不改变导航坐标，也不发送运动命令。

### 2.10 性能模拟、512 深度档位和 Nav2 未激活

用户要求先模拟冲突/延迟，再修复模拟中发现的问题。之后现场仍报告数据超时，用户明确选择：

> 降到 512，优先实时性

因此只对 Nav2 深度任务应用 512 上限，保留原相机画面和人物检测输入；该选择可能损失细小障碍深度细节，不能宣称完全消除延迟。

选点模式在视觉障碍未开启时能走、人物模式开启视觉时不能走，说明对比变量不仅是“选点/人物”，还包括视觉链负载和新鲜度门控。R40 继续把投影、复核和语义工作移出关键控制锁。最后“Nav2 未激活”经 R41 追到自有插件构建被 Conda C++ 运行库污染，改为隔离系统 ROS/C++ 工具链重建；系统 Nav2、Conda 本身和旧库没有被改写。


## 3. R01～R42 需求、公开结论与当前实现

### R01：地图、雷达与叠加模式

**用户请求**

> 添加，并且设置为雷达模式和地图模式可以选择开启，可以单独开启一个也可以同步开启

**公开回复/结果**

增加 `radar`、`map`、`both` 三种障碍来源，使用启动变量选择；切换模式前停车并重启，不在行驶中热切换。

**公开分析与证据**

静态地图和雷达的坐标、更新频率和故障方式不同。启动时固定来源可使代价地图配置确定，也便于单独排查雷达误检或地图错误。

**当前文件**

- `follow.launch.py`
- `params.yaml`
- `map_startup.py`
- `maps/corridor.yaml`
- `README.md`

**验证与限制**

启动就绪检查可以阻止缺少 map server/lifecycle 服务的半启动状态。地图模式不能发现地图中没有的临时障碍；雷达/叠加模式仍依赖雷达话题、TF 和数据时效。

### R02：网页显示地图、车位和路线

**用户请求**

> 地图可不可以在网页前端呈现，需要标注的有地图，小车当前位置，小车预计路线

**公开回复/结果**

网页只读接口提供静态/代价地图、车身、当前位姿和规划路径；画布用统一世界坐标变换绘制。

**公开分析与证据**

显示层用于观察，不能成为运动授权。过期图层隐藏或显示错误，避免把旧路径/旧位姿当成当前状态。

**当前文件**

- `obstacle_view.py`
- `frontend/obstacle-map.js`
- `route_preview.py`

**验证与限制**

地图约每 0.5 秒刷新，超过时效的图层隐藏。路径只有在规划成功并仍有效时显示；网页正常不代表底盘已执行。

### R03：矩形与自由手绘禁区

**用户请求**

> 可不可以在网页添加一个现场绘制大概地图的功能，不止矩形，跟随鼠标或者手指绘画

**公开回复/结果**

增加矩形和连续笔画，支持鼠标/触摸；提交时检查坐标范围、点数、地图版本并生成编辑层。

**公开分析与证据**

浏览器坐标必须逆变换到地图坐标，缩放/平移后仍需落到同一世界位置。编辑层与原始静态图分离，便于撤销和清除。

**当前文件**

- `nav2_map_edit.py`
- `nav2_map_publisher.py`
- `frontend/obstacle-map.js`
- `obstacle_view.py`

**验证与限制**

手绘只是人为近似，不能替代现场测量；提交后需等编辑图发布并重新规划。普通照片上传方案已按用户要求撤回。

### R04：地图外边界红区

**用户请求**

> 不是你这样添加，就在上传的地图四周添加红色区域就行了

**公开回复/结果**

边界放在原地图四周外侧，不把整个内部走廊或大面积视觉候选涂成禁区；地图原点随外扩格正确补偿。

**公开分析与证据**

红边的职责是阻止完整车身驶出已知地图，不能侵占原本可通行的内部净宽。视觉候选在地图外时不应反投到内部。

**当前文件**

- `boundary_map.py`
- `nav2_map_publisher.py`
- `frontend/obstacle-map.js`

**验证与限制**

边界只代表地图范围，不代表地图外实际存在实体墙。旋转地图和原点补偿由测试覆盖；真实初始对齐仍需人工完成。

### R05：红黄虚拟墙共用相机预览

**用户请求**

> 黄色虚拟墙不需要新增一个视频口，合并在红色虚拟墙的那个窗口里面

**公开回复/结果**

手绘禁区用红色、视觉疑似障碍用黄色，叠加到同一停车快照预览；原实时相机画面保持独立。

**公开分析与证据**

共用窗口便于比较两类墙，但颜色来源必须分离，清除手绘层不能顺带清除视觉候选。

**当前文件**

- `virtual_wall.py`
- `frontend/virtual-wall.js`
- `vision_layer.py`

**验证与限制**

这是近似投影，依赖相机高度、俯角、内参、深度和车位；不能当成实时增强现实测量。预览不直接发送运动控制。

## 4. 当前完整公开逻辑链

### 4.1 选点模式

1. 用户在小地图选择地图内终点。
2. 后端取得当前位姿和配置快照。
3. Nav2 计算候选路径。
4. 自有整车复核用完整全局/局部证据检查车身、转弯扫掠、地图边缘、手绘区、障碍和可选紫色硬缓冲。
5. 页面只显示通过复核的预览路线。
6. 用户点击开始行驶。
7. 后端复核路线序号、起点、时效、配置、强停和传感器，原子授权。
8. FollowPath 速度经过时效、近距危险和实际扫掠检查后进入原唯一底盘发布通道。
9. 完成、取消、长期超时或无可绕路线后停车。

### 4.2 人物单段模式

1. 选择人物 ID。
2. 从同帧有效距离/方位和 TF 计算世界坐标。
3. 点击规划时冻结最近有效人物历史点。
4. 生成保留跟随距离的停车终点，并按选点同样方式规划/整车复核。
5. 点击开始追踪时执行该锁定路线。
6. 途中人物图标闪烁、移动或测量过期不改变本段终点。
7. 新障碍触发停车；能绕行则保持同一终点重规划，不能绕行则停车。
8. 本段完成后结束，不自动续段。

### 4.3 人物连续模式

1. 首段与单段相同。
2. 成功到达历史点附近后才读取新的有效人物观测。
3. 人物距离不大于约 1 米时等待。
4. 人物重新离开 1 米范围且观测有效时，建立下一段。
5. 每段途中终点冻结，除新障碍处置外不随人物每帧重规划。
6. 用户取消、传感器长期故障、无可行路径或授权失效后停止循环。
7. 代际/任务 ID 阻止已取消旧回调重新启动运动。

### 4.4 视觉障碍链

1. 深度结果通过最新值邮箱进入 Nav2 自有视觉层，保留真实采集时间。
2. R39 只对新 Nav2 深度任务应用 512 上限。
3. 每帧基础投影和连通域只计算一次。
4. 全量安全点用于近距和扫掠；地图候选、最近显示候选、相机黄色墙使用各自筛选，互不误删。
5. 额外 YOLOE 受预算控制，深度链不健康时暂停提交。
6. 短暂视觉过期先输出零速等待；恢复前复核完整证据。
7. 超过长期上限、真实危险或无可行绕路线时取消并保持停车。

## 6. 源码归属与注释规则

本次注释补齐应遵循：

- 文件顶部：说明文件职责、关联需求 R 编号、当前添加/修改逻辑和关键边界。
- 主要类/函数：说明输入、输出、状态所有权、失败关闭策略及为什么不能放宽。
- 复杂并发：说明快照、代际、锁外计算、短锁提交和关闭时资源归属。
- 测试：说明验证的是哪类故障，明确“不连接实车”。
- C++/CMake：说明几何/搜索/插件/依赖/安装/测试各分组职责。
- YAML/XML：使用格式允许的注释；JSON、PGM、模型权重和二进制文件不强行插入注释。
- build、install、日志、缓存和运行生成结果不作为源码修改。
- 不认领无法由当前文件和记录证明的旧代码，不为别人代码补上“自有”标签。
